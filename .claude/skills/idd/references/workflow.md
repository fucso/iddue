# IDD ワークフロー（Issue 中心の開発フロー）

GitHub Issues を起点とした開発ワークフローの全体像。

---

## 全体フロー

```
Issue 作成 → 要件・設計の議論 → docs 更新 → 実装・PR 作成 → マージ
```

---

## フロー詳細

### 1. Issue 作成

クライアント案件、不具合対応、社内での機能追加・改善などを GitHub Issue として起票する。

### 2. 要件・設計の議論

Issue 上で要件の具体化・設計方針の議論を行う。

Issue の要件では実装レベルでの具体的な対応方針が決めきれない、決まったがスコープが大きすぎる場合は Sub Issue に分割する。
Sub Issue のある Issue については、配下の Sub Issue の結果を集約することで Issue の要件を満たすことを目的とする。

**実装可能な Issue の目安:**
- 変更対象ファイルが特定できる
- 実装内容が明確である
- 完了条件（受け入れ基準）が定義されている
- 1エージェントまたは1開発者が完結できる範囲である

### 3. docs 更新（必要な場合）

具体的な要件・仕様・設計・対応方針が決まり、**現行の `docs/specs/` との差異がある場合**は新しい仕様で docs をアップデートし Issue に紐付けた PR を作成する。

- `docs/specs/` はコードの変更と同一の PR で変更し、**その Issue 完了時点の正確な仕様**を記録する
- リファクタリングなどのドキュメントレベルでの仕様変更がない場合は docs 更新は不要

### 4. 実装

Issue で策定した対応方針・現行コード・`docs/specs/` の仕様を踏まえて実装を開始し、Issue PR に push、または PR を作成する。

実装中に仕様変更が発生した場合は `docs/specs/` を同一 PR 内で更新し、変更理由を Issue にコメントで記録する（詳細は [docs.md](docs.md) を参照）。

### 5. PR マージ

Issue の要件（完了条件）を満たせていれば PR をマージする。

- PR マージにより `Closes #NNN` で紐付けた Issue が自動クローズされる
- 完了条件を満たせていない場合はレビューで差し戻し、Issue にコメントで理由を記録する

---

## PR 作成ルール

- PR 本文に `Closes #NNN` を含め Issue にリンクする（マージ時に Issue が自動クローズ）
- `docs/specs/` の変更はコードと同一の PR に含める
- 1つの Issue に対して原則1つの PR を作成する
