# 観点③: 設計整合性

## 目的

Issue に定義された設計（スコープ・対象ファイル・インターフェース設計）と実際の実装が整合しているかを確認する。
設計逸脱は要件未充足や CI 失敗の根本原因になりうるため、CI チェックより先に確認する。

---

## モード判定

`sub_issues` の有無によって参照するドキュメントが異なる。

| モード | 条件 | 設計の参照元 |
|--------|-----|-------------|
| **オーケストレーション** | `sub_issues` が空でない | `config.yaml`（各サブ Issue の設計定義） |
| **単独 Issue** | `sub_issues` が空 | Issue 本文 / Issue YAML（`.iddue/issue/{parent}.yaml`） |

---

## 入力

### オーケストレーションモード

| データ | 参照元 |
|--------|--------|
| config.yaml | worktree: `.worktree/iddue-review/{parent}/.orchestrate/config.yaml` |
| 各サブ `implement.md` | worktree: `.worktree/iddue-review/{parent}/.orchestrate/reports/{sub}/implement.md` |
| 変更後のソースコード全体 | worktree: `.worktree/iddue-review/{parent}/{変更ファイルパス}` |
| 変更内容（差分） | Phase 2 で取得した `gh pr diff` の出力 |
| 各サブ Issue 本文 | Phase 2 で取得済み |

### 単独 Issue モード

| データ | 参照元 |
|--------|--------|
| 親 Issue 本文 | Phase 2 で取得済み（`gh issue view` の結果） |
| 親 Issue YAML（任意） | worktree: `.worktree/iddue-review/{parent}/.iddue/issue/{parent}.yaml` |
| 変更後のソースコード全体 | worktree: `.worktree/iddue-review/{parent}/{変更ファイルパス}` |
| 変更内容（差分） | Phase 2 で取得した `gh pr diff` の出力 |

---

## 判定基準

以下はオーケストレーション・単独 Issue 共通の基準。設計ドキュメントの参照先がモードによって異なる。

### CRITICAL（フロー停止・COMMENT）

設計（config.yaml または Issue 本文）から以下のような **記載なしの逸脱** がある場合：

| 逸脱の種類 | 例 |
|-----------|---|
| スコープ外のファイルを変更 | 設計に含まれないクラスや DB テーブルを変更 |
| インターフェース変更 | メソッドシグネチャ・API レスポンス形式・引数の追加削除 |
| 設計とは異なる実装アプローチ | 指定された手法と別の手法を採用 |
| スコープの欠落 | 設計に含まれるが変更後コードに存在しない |

**逸脱と判定しない例（WARNING または OK）:**

| 内容 | 扱い |
|------|-----|
| テストの追加・充実 | OK |
| 実装範囲内の軽微なリファクタリング | OK |
| コメントや命名の改善 | OK |
| Issue 本文 / implement.md に理由が記載された意図的な設計変更 | WARNING（内容を確認して判断） |

### WARNING

以下の場合は CRITICAL にせずフローを継続するが、APPROVED コメントに付記する：

- Issue 本文や implement.md に「設計から変更した」旨の記載はあるが、変更内容が軽微でない
- スコープ外への軽微な波及（依存関係の整理など）

### OK

設計ドキュメント（config.yaml または Issue 本文）と実装（変更後コード）が整合している。

---

## レビューフロー

### オーケストレーションモードの場合

1. config.yaml の `tasks` 配下から各サブ Issue の設計定義を把握する
   - スコープ（対象ファイル・クラス・機能）
   - インターフェース設計（メソッドシグネチャ・引数・戻り値）
   - 実装アプローチの指示
2. 変更ファイル一覧と設計スコープを照合する（スコープ外ファイルの変更を検出）
3. 各変更ファイルについて worktree からコード全体を `Read` して設計との整合を確認する
4. implement.md の「変更ファイル一覧」「実装サマリー」と設計を照合する
   - implement.md に理由が記載されている場合は意図的変更として扱う
5. 逸脱の有無を判定し CRITICAL / WARNING / OK に分類する
6. CRITICAL が 1 件でもあれば → コメント投稿してフロー終了（cleanup 実行）
7. CRITICAL なし → 次の観点へ

### 単独 Issue モードの場合

1. Issue 本文から設計意図・対象スコープ・実装方針を読み取る
   - 「## 設計」「## 実装方針」「## 対象ファイル」「## 完了条件」などのセクションを確認
   - セクションがない場合は Issue 全体から対象範囲・変更内容の意図を読み取る
   - Issue YAML が存在する場合は補足情報として参照する
2. 変更ファイル一覧と Issue から読み取ったスコープを照合する
3. 各変更ファイルについて worktree からコード全体を `Read` して Issue の意図との整合を確認する
   - インターフェース（メソッド定義・API 仕様）が Issue の記述と一致しているか確認
4. 逸脱の有無を判定し CRITICAL / WARNING / OK に分類する
5. CRITICAL が 1 件でもあれば → コメント投稿してフロー終了（cleanup 実行）
6. CRITICAL なし → 次の観点へ

---

## コメントフォーマット

### 問題あり（CRITICAL）

`SKILL.md Phase 4.1` の COMMENT で投稿。
逸脱箇所が diff の特定の行に紐づけられる場合はインラインコメントも付ける。

#### オーケストレーションモード

**サマリー本文（`body`）:**
```markdown
## AI Review — 観点③設計整合性

設計から逸脱している箇所が見つかりました。
要件・CI のレビューは設計が確定した後に実施します。

### #{sub}: {サブ Issue タイトル}

**逸脱内容**: {逸脱の説明}
**元の設計（config.yaml）**: {config.yaml の該当記述}
**実際の実装**: {変更後コード（worktree）または implement.md から確認した内容}

{複数サブ Issue に逸脱がある場合は各サブ Issue ごとに繰り返す}

{WARNING がある場合}
### 注意（ブロックはしていないが確認推奨）

- #{sub}: {WARNING の内容}
```

#### 単独 Issue モード

**サマリー本文（`body`）:**
```markdown
## AI Review — 観点③設計整合性

Issue の設計・スコープから逸脱している箇所が見つかりました。
要件・CI のレビューは設計が確定した後に実施します。

**逸脱内容**: {逸脱の説明}
**Issue の記述**: {Issue 本文の該当箇所}
**実際の実装**: {変更後コード（worktree）から確認した内容}

{WARNING がある場合}
### 注意（ブロックはしていないが確認推奨）

- {WARNING の内容}
```

**インラインコメント（紐づけ可能な場合）:**
```json
{
  "path": "{変更ファイルパス}",
  "line": {問題の行番号},
  "body": "Issue の設計では {元の設計} だが、この変更は設計外のスコープに変更を加えています。"
}
```

### 問題なし（OK → 次の観点へ）

コメント投稿はしない。内部メモとして以下を記録：

```
（オーケストレーション）観点③ 設計整合性: ✅ {N} サブ Issue すべて設計と整合
（単独 Issue）観点③ 設計整合性: ✅ Issue のスコープ・設計と整合
{WARNING があれば件数を記録}
```
