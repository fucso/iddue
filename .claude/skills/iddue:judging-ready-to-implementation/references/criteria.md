# 判定基準

以下の4項目を評価し、**すべてを満たす**場合のみ「実装可能」と判定する。

## 1. 変更対象ファイルが特定できるか

Issue に明示されていなくても、記載内容から**再現可能に推論できる**ことが条件。何度判定しても同じファイルが特定できる状態であればよい。

| 判定 | 状態 |
|------|------|
| ✅ | ファイルが明示されている |
| ✅ | ディレクトリのみの記載でも、配下のファイルが1つのみ、または配下のファイル全体が対象であることが明確 |
| ✅ | 機能・クラス・エンドポイント名など、コードベースを探索すれば一意に特定できる情報がある |
| ✅ | Issue に記載のファイル・機能を利用している呼び出し元ファイルは、実装時に探索して修正するため対象外でよい |
| ❌ | 「APIを修正する」「モデルを更新する」など、複数の候補が存在し一意に絞り込めない抽象的な記述のみ |

## 2. 実装内容が明確か

変更の種類ごとに必要な具体性が異なる。以下の代表的なケースを参照して判定する。

### パラメーター追加・変更

| 判定 | 状態 |
|------|------|
| ✅ | パラメーター名・型・必須/任意・バリデーション条件・受け取った値の振る舞いがすべて明記されている |
| ❌ | 「〜パラメーターを追加する」とだけあり、型やバリデーション、振る舞いが不明 |

例（✅）: `duration` パラメーター（整数、必須、1〜12の範囲）を追加し、契約期間のフィルタリングに使用する

### ロジック変更・条件分岐の追加

| 判定 | 状態 |
|------|------|
| ✅ | 変更前後の条件・分岐の内容、影響を受けるケースが明記されている |
| ❌ | 「計算ロジックを修正する」など変更前後の差分が不明 |

例（✅）: 現在は `base_rate` のみで計算しているが、`is_renewable` フラグが true の場合は `renewable_rate` を使うよう変更する

### バリデーション追加

| 判定 | 状態 |
|------|------|
| ✅ | 検証対象・条件・エラー時のレスポンス（ステータスコード・メッセージ）が明記されている |
| ❌ | 「バリデーションを追加する」だけでエラー条件やレスポンスが不明 |

例（✅）: `start_date` が未来日の場合は 422 Unprocessable Entity を返し、`"start_date must be in the past"` メッセージを含める

### レスポンス構造の変更

| 判定 | 状態 |
|------|------|
| ✅ | 追加・変更・削除するフィールド名・型・値の意味が明記されている |
| ❌ | 「レスポンスに情報を追加する」だけでフィールド名や型が不明 |

### 共通判定

| 判定 | 状態 |
|------|------|
| ❌ | 「検討する」「調査する」「設計する」など、実装でなく調査・設計段階の作業が中心 |

## 3. 完了条件が定義されているか

エージェントが**自力で完了を検証できるか**を基準にする。完了条件は明示されていなくても、基準2の実装内容が十分に具体的であれば「その実装が正しく動くこと」として暗黙の完了条件とみなしてよい。

| 判定 | 状態 |
|------|------|
| ✅ | 特定の入力に対して特定のレスポンスが返ること（入力・出力例が明記されている） |
| ✅ | 特定のケースでエラーになること（ステータスコード・メッセージが明記されている） |
| ✅ | 追加すべきテストケースの内容が明記されている |
| ✅ | 実装内容が十分に具体的で、完了が自明に判断できる |
| ❌ | 「動作すること」「適切に処理されること」など、何をもって完了とするか判断できない |
| ❌ | 「要件を満たすこと」など人間の主観的な確認が必要な記述のみ |
| ❌ | 「テストが通ること」のみで、何のテストか・どんなケースかが不明 |

## 4. 1エージェントで完結できる範囲か

ファイル数ではなく**1つの関心事で完結するか**を基準にする。

| 判定 | 状態 |
|------|------|
| ✅ | 1つの機能・1つのバグに対する変更（ファイル数不問） |
| ✅ | 変更が1つの論理的なまとまりで完結し、単独でPRを作れる |
| ❌ | 複数の独立した機能を同時に変更する |
| ❌ | 他の未マージPRの完了を前提とする |
| ❌ | DBスキーマ・API・外部連携など複数レイヤーにまたがる大規模変更 |
