# idd:open レベル定義と判定基準

## レベル一覧

| レベル | 定義 | 委譲先スキル |
|--------|------|-------------|
| `concrete` | 変更対象ファイル・実装内容・完了条件が具体的に把握できている（`idd:judging-ready-to-implementation` をパスできる水準） | `idd:open:concrete` |
| `bug` | 具体的なエラーログ・アラート・Bugsnag URL など、起きた事象が明確 | `idd:open:bug` |
| `problem` | 問題は明確（リファクタリングの必要性・設計上の問題など）だが、対応方法・対象ファイルは未定 | `idd:open:problem` |
| `idea` | 将来の機能追加・改修アイデアなど、問題・解決策ともに漠然としている | `idd:open:idea` |

## 判定基準

レベルはキーワードではなく**引き出せた情報の詳細度**で判定する。

### 判定フロー

```
エラーログ・Bugsnag URL・アラートなど事象の証拠がある？
  → YES: bug

変更対象ファイルと実装内容が具体的に特定できる？
  → YES: concrete

問題・課題を具体的に特定できる（どこが・なぜ問題か言える）？
  → YES: problem

それ以外（方向性レベルのアイデア）
  → idea
```

### problem と idea の見分け方

迷う場合の判断基準：

- **problem**: 「〇〇クラスが肥大化していて保守しにくい」「〇〇の処理が重複している」など、問題箇所を具体的に指摘できる
- **idea**: 「〇〇機能があると便利そう」「〇〇を改善したい」など、まだ問題自体の輪郭が曖昧

問題が具体的に特定できているなら `problem`、そうでなければ `idea` に倒す。
