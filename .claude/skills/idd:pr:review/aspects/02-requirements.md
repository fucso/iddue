# 観点②: 要件充足性

## 目的

親 Issue の要件・完了条件が実装によって充足されているかを確認する。

---

## 入力

### 共通（単独 Issue / オーケストレーション共通）

| データ | 参照元 |
|--------|--------|
| 親 Issue 本文 | Phase 2 で取得済み（`gh issue view` の結果） |
| 親 Issue YAML（任意） | worktree: `.worktree/idd-review/{parent}/.idd/issue/{parent}.yaml` |
| 変更後の実装コード全体 | worktree: `.worktree/idd-review/{parent}/{変更ファイルパス}` |
| 関連する未変更ファイル | worktree から必要に応じて `Read`（変更ファイルが依存するファイル等） |
| 変更内容（差分） | Phase 2 で取得した `gh pr diff` の出力 |

### オーケストレーションモードのみ

| データ | 参照元 |
|--------|--------|
| 各サブ Issue 本文 | Phase 2 で取得済み |
| 各サブ `implement.md` | worktree: `.worktree/idd-review/{parent}/.idd/orchestration/reports/{sub}/implement.md` |

---

## 判定基準

### CRITICAL（フロー停止・REQUEST_CHANGES）

親 Issue の「完了条件」「要件」「受け入れ基準」に **明示された** 項目が以下の状態にある場合：

| 状態 | 判定 |
|------|-----|
| 実装されていない（変更後コードにも implement.md にも言及なし） | CRITICAL |
| 実装の意図はあるが変更後コードを見ると明らかに動作しない | CRITICAL |

### WARNING

以下の場合は CRITICAL にせずフローを継続するが、APPROVED コメントに付記する：

| 状態 | 判定 |
|------|-----|
| テストが不十分（ハッピーパスのみ、エラーケースなし）| WARNING |
| 要件は満たしているが実装方法がリスクをはらんでいる | WARNING |
| 要件として明示されていないが想定されるケースが未対応 | WARNING |

### OK

親 Issue の全明示要件が変更後コード（worktree）で確認できる。

---

## レビューフロー

1. 親 Issue 本文から要件を構造化して抽出する
   - 「## 完了条件」「## 要件」「## 受け入れ基準」などのセクションを確認
   - チェックリスト（`- [ ]`）形式の項目を優先的に抽出
   - セクションがない場合は Issue 全体から要件を読み取る
2. 各要件について worktree からコードを読んで充足状況を確認する
   - **オーケストレーション**: 要件ごとに担当サブ Issue を特定し、implement.md の実装サマリーで概要を把握した上でコードを確認する
   - **単独 Issue**: 変更ファイル一覧を起点に、worktree のコードを `Read` して要件を充足しているか直接確認する
   - diff で「変更前後」を確認しつつ、worktree で「変更後の全体像」を把握する
   - 必要に応じて変更ファイルが呼び出すクラス・メソッドのファイルも worktree から参照する
3. 未対応・不十分な要件を特定し CRITICAL / WARNING に分類する
4. CRITICAL が 1 件でもあれば → コメント投稿してフロー終了（cleanup 実行）
5. CRITICAL なし → 次の観点へ

---

## コメントフォーマット

### 問題あり（CRITICAL）

`SKILL.md Phase 4.1` の REQUEST_CHANGES で投稿。
要件が特定のコード箇所に紐づけられる場合はインラインコメントも付ける。

**サマリー本文（`body`）:**
```markdown
## AI Review — 観点②要件充足性

親 Issue の要件が未対応または不十分です。

| # | 要件 | 判定 | 詳細 |
|---|-----|------|-----|
| 1 | {要件の内容} | ❌ 未対応 | 変更後コードに実装が確認できない |
| 2 | {要件の内容} | ❌ 不十分 | {具体的な不足点} |

{WARNING がある場合}
### 注意（ブロックはしていないが確認推奨）

| # | 要件 | 判定 | 詳細 |
|---|-----|------|-----|
| 3 | {要件の内容} | ⚠️ テスト不十分 | エラーケースのテストが不足 |
```

**インラインコメント（紐づけ可能な場合）:**
```json
{
  "path": "{変更ファイルパス}",
  "line": {問題の行番号},
  "body": "要件「{要件の内容}」を満たすためにはこの箇所で {必要な処理} が必要です。"
}
```

### 問題なし（OK → 次の観点へ）

コメント投稿はしない。内部メモとして以下を記録：

```
観点② 要件充足性: ✅ 全 {N} 件の明示要件が充足
{WARNING があれば件数を記録}
```
