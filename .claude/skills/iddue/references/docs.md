# docs/specs/ によるローカルドキュメント管理

IDDUE ワークフローにおけるローカルドキュメント（`docs/specs/`）の目的・管理方針・更新ルール。

## 目的

### コミットに紐付いた仕様の記録

`docs/specs/` のドキュメントはコードと同じブランチ・コミットに含まれる。
これにより、**任意の過去コミットをチェックアウトした時点での正しい仕様を確認できる**。

バグ調査・リリース後の仕様確認・レビュー時に、GitHub Issue の議論を辿る必要がなく、
コミット時点の `docs/specs/` を参照するだけでよい。

### GitHub Issues との役割分担

| | GitHub Issues | docs/specs/ |
|---|---|---|
| **用途** | 開発管理（要件定義・タスク管理・議論・進捗追跡） | 仕様と意思決定の記録のドキュメンテーション |
| **記録するもの** | 要件・タスク・議論・進捗 | 仕様（WHAT）と意思決定の経緯・根拠（WHY） |
| **更新方法** | コメント追加、本文更新 | ファイル編集＋コードと同一コミット |
| **参照タイミング** | 開発の進捗・タスク状況を確認したいとき | 実装・レビュー・バグ調査・設計の背景を知りたいとき |

**GitHub Issues = 開発管理の場**

要件の定義・タスクの起票・進捗の追跡・実装上の議論など、開発を進めるための作業を行う。

**docs/specs/ = 仕様と意思決定の記録**

「このバージョンで実装された仕様は何か」「なぜその設計になったのか」を迷いなく確認できる状態を維持する。
仕様の内容（WHAT）だけでなく、その設計に至った意思決定の経緯・根拠（WHY）もここに記録する。

---

## docs/specs/ に記載するもの

### 記載する内容

- **エンドポイント仕様**: パラメータ一覧・バリデーション・レスポンス JSON 例
- **データモデル**: テーブル定義・フィールドの意味・ER 図
- **アーキテクチャ設計・実装方針**: 採用したパターン・既存コードとの関係
- **意思決定記録（ADR）**: 採用した設計の結論・根拠・背景（検討した選択肢や議論の過程は Issue に記録し、決定の内容と理由をここに記載）

### 記載しないもの

- **スケジュール・期限**: 時間軸に依存する情報は Issue で管理
- **タスクの進捗状況**: 開発管理は Issue で行う
- **コードそのもの**: リポジトリで管理

## 更新タイミング

### 仕様変更時（最重要）

仕様が変わった場合は、**同一 PR（同一 Issue の管轄下）** でドキュメントとコードの両方を更新する。
メインブランチから見てドキュメントとコードが同一 PR で整合していればコミットは分けてもよい。

```
仕様変更確定 → docs/specs/ 更新コミット → コード実装コミット → 同一 PR でマージ
```

あるいは同一コミットにまとめても構わない。どちらの場合も PR 単位での整合性が担保される。

**ドキュメント先行フローの例:**

1. Issue の議論で仕様変更が確定
2. `docs/specs/` のみを変更して Issue に紐付いた PR を作成
3. ドキュメントとコードの差分を見ながら実装を進め、同じ PR に push

このフローはドキュメントの差分を実装の仕様書として活用できる利点がある。

### 仕様変更時の GitHub Issue への記録

仕様変更が発生した場合、その理由・背景を対象 Issue にコメントとして残す。

```markdown
## 仕様変更: {変更箇所の概要}

**変更前**: {旧仕様}
**変更後**: {新仕様}
**変更理由**: {なぜ変更が必要になったか}
**影響範囲**: {他の機能・タスクへの影響}
```

`docs/specs/` には変更後の正しい仕様と、変更理由（なぜ変更したか）を記載する。Issue はその変更を起点とした開発管理（タスク更新・影響範囲の追跡など）に使う。

## 実装フロー中の更新判断

`/iddue:start` による実装中、以下のケースで `docs/specs/` を更新する：

| ケース | 対応 |
|--------|------|
| 実装中に仕様変更が発生した | docs/specs/ を更新。Issue にコメントで変更理由を記録 |
| Issue に記載のない仕様の詳細が実装で明確になった | docs/specs/ に追記。コードと同一コミット |
| エンドポイント仕様・レスポンス形式が確定した | docs/specs/ に詳細仕様を記載 |
| Issue の記載通りに実装できた（仕様変更なし） | docs/specs/ の更新は原則不要 |

---

## ファイル構造

```
docs/specs/
├── README.md                # インデックス（一覧・概要・関連 Issue）
└── {feature-name}.md        # 機能ごとの仕様書（常に最新の正しい情報のみ）
```

**命名規則:** ドメイン、機能名を英字・ハイフン区切りに変換
- `検針日対応` → `meter-reading-date.md`
- `エンドポイントパラメータリファクタリング` → `endpoint-params-refactoring.md`
