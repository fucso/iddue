# `/iddue:open:bug` — 不具合起票

バグや予期しない動作を GitHub Issue として記録する。
`iddue:open` からの委譲でも、直接呼び出しでも動作する。

## 使い方

```
/iddue:open:bug
/iddue:open:bug ガスプラン一覧APIで500エラーが返ってくる
```

---

## 実行内容

### Phase 1: エラー分析

呼び出し時に与えられた情報（引数の説明文・エラーメッセージ・ログ・URL など）をもとにエラーを分析する。

**分析観点：**
- エラーの種類（例: 500エラー、バリデーションエラー、タイムアウト、データ不整合など）
- 発生箇所の推定（API エンドポイント、サービス層、DB クエリ、外部連携など）
- 考えられる原因の候補
- 影響範囲の見当（特定ユーザー・全体・特定条件下など）

分析結果をユーザーに報告する。原因が特定できた場合や対応方針が絞り込める場合は、修正・調査の方向性をサジェストする。

```
## エラー分析結果

**エラーの種類:** {種類}
**推定発生箇所:** {箇所}
**考えられる原因:**
- {原因1}
- {原因2}（あれば）

**影響範囲の見当:** {影響範囲}

**対応方針の候補:**（原因が明確な場合のみ）
- {方針1}
- {方針2}（あれば）
```

ユーザーと対話しながら対応方針を確定させてから Phase 2 へ進む。
情報が少なく分析できない場合はその旨を伝えて Phase 2 へ進む。

### Phase 2: 情報収集（対話形式）

エラー分析の結果をもとに、Issue に記録すべき情報をユーザーとの対話形式で収集する。
Phase 1 の分析結果・対応方針をもとに以下の情報を収集する。

| 項目 | 説明 | 必須 |
|------|------|------|
| タイトル | Issue タイトルの核となる1行の概要 | ✅ |
| 再現手順 | 不具合を再現するための手順（番号付きリスト） | ✅ |
| 期待される動作 | 本来どうなるべきか | ✅ |
| 実際の動作 | 何が起きているか（エラーメッセージ含む） | ✅ |
| 発生頻度・影響範囲 | 毎回か特定条件のみか、影響するユーザー・機能 | ✅ |
| 関連情報 | ログ・Bugsnag URL・スクリーンショットなど | 任意 |
| 親 Issue 番号 | 親となる Issue の番号 | 任意 |

収集が完了したら内容をユーザーに確認してもらう。

### Phase 3: タスク分割の検討（条件付き）

**Phase 1 で対応方針が確定した場合のみ実施する。**
対応方針が未確定・調査が必要な段階の場合はスキップして Phase 4 へ進む。

起票する内容を複数の Sub Issue に分割すべきか検討する。

以下の場合は分割を提案する：
- 原因調査と修正実装を別タスクとして切り出したい
- 複数箇所の修正が独立して実施できる

分割する場合は各 Sub Issue のタイトルと概要案を提示してユーザーに確認する。
確定した分割案は Phase 4 で親 Issue を作成した後に Sub Issue として登録する。

分割しない場合はそのまま Phase 4 へ進む。

### Phase 4: オーダーシート作成・Issue 起票

収集した情報から create オーダーシートを作成する。
各フィールドにはできるだけ詳細に情報を記載する。情報を省略・要約せず、収集したすべての情報を記録すること。

ファイル名: `.iddue/orders/{YYYYMMDD-HHMMSS}-create.yaml`

```yaml
type: create
parent_issue: {親 Issue 番号または null}
labels:
  - "iddue"
  - "level:bug"

objective:
  what: "{不具合の概要・修正の目的}"
  why: |
    {エラーの詳細・再現手順・期待される動作・実際の動作・影響範囲}
  how: "{対応方針（確定している場合）}"  # 未確定の場合は省略
  detail:
    - type: design
      target: "{修正対象ファイル・箇所（判明している場合）}"
      change: "{修正内容}"
    # 調査フェーズで対象が未確定の場合は detail を省略
```

作成したオーダーシートの内容をユーザーに確認する。
確認後、`iddue:create-issue` スキルで Issue を作成する。

```
/iddue:create-issue .iddue/orders/{ファイル名}
```

Phase 3 でタスク分割が確定している場合は、親 Issue 作成後に各 Sub Issue について
それぞれ create オーダーシートを作成し `iddue:create-issue` で登録する（`parent_issue` に親 Issue 番号を指定）。

Issue 作成後、**Phase 1 で対応方針が確定している場合**は `iddue:judging-ready-to-implementation` スキルで実装可否を判定する。

```
/iddue:judging-ready-to-implementation {作成した Issue 番号}
```

判定結果に応じて次のアクションをユーザーに提示する：
- 実装可能 → `/iddue:start {NNN}` で実装を開始できることを案内
- 実装不可 → 不足内容と推奨アクションを提示

### Phase 5: 完了報告

```
✅ /iddue:open:bug 完了

- Issue: [#{NNN}] {タイトル}
  URL: {URL}

## 次のステップ
{実装可否判定の結果に応じた案内。判定を実施しなかった場合は以下のデフォルト文言}
修正の実装を開始する: /iddue:start {NNN}
```

---

## エラーハンドリング

| エラー | 対応 |
|--------|------|
| Issue 作成失敗 | エラーメッセージを表示して終了 |
| Sub Issue 登録失敗 | 警告を表示してフローを継続（手動での登録方法を案内） |
